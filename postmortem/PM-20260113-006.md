## 问题描述

### 现象
- 项目中存在 `web/bun.lock` 锁文件，可能导致依赖版本锁定问题
- 依赖安装过程可能使用了缓存，导致某些场景下依赖不一致或更新不及时
- 766 行的 lockfile 被完全移除

### 根因分析
1. **为什么移除 bun.lock？**
   - lockfile 可能导致依赖版本固化，在某些环境下无法获取最新的补丁版本

2. **为什么添加 --no-cache 参数？**
   - 缓存可能导致依赖安装不一致，特别是在 CI/CD 环境或多人协作时
   - 强制从源重新下载可以确保依赖的新鲜度和一致性

3. **为什么这是必要的？**
   - 可能遇到了依赖版本不一致导致的构建或运行时问题
   - 需要确保每次安装都获取符合 package.json 语义化版本范围的最新版本

4. **为什么不保留 lockfile？**
   - 项目可能处于快速迭代阶段，需要灵活的依赖管理
   - 或者团队决定采用更激进的依赖更新策略

5. **根本原因**
   - 依赖管理策略调整：从严格锁定版本转向更灵活的版本管理
   - 可能是为了解决特定的依赖冲突或版本不一致问题

### 影响评估
- **用户影响**: 
  - 短期：可能导致构建时间增加（无缓存）
  - 长期：可能因依赖版本不固定导致潜在的不稳定性
  
- **系统影响**: 
  - 依赖安装行为改变，每次都会重新解析版本
  - CI/CD 构建时间可能增加
  - 不同环境可能安装不同的依赖版本（在语义化版本范围内）
  
- **数据影响**: 无数据损坏或丢失

## 后续进展（2026-07-26）

上文「建议后续行动」第 2 条已被触发：无 lockfile 的策略确实引发了依赖版本问题，
本节记录决策推翻的经过。

### 触发事件

Dependabot PR #118 将 `typescript` 从 6.0.3 升到 7.0.2 并合入 main。
`typescript-eslint` 尚不支持 TS 7（见
[typescript-eslint#10940](https://github.com/typescript-eslint/typescript-eslint/issues/10940)），
在 CI 的 `bun run lint` 步骤直接抛错退出，main 分支的前端流水线随之全部失败。

### 值得注意的事实

该 PR 的 CI **本身就是红的**（`pull_request` 运行结果为 failure），但仍被合入 main。
也就是说，本次事故的直接原因并不是 CI 没能发现问题，而是**带着失败检查的 PR 被合并**。
lockfile 的缺失不是这次事故的根因，但它放大了风险面：没有锁文件时，
即使代码毫无变化，`bun install` 每次都会重新解析 `^`/`~` 范围，
上游任何一次发版都可能让此前通过的构建突然失败，且没有可回滚的依赖差异记录。

### 已采取的措施

1. `typescript` 固定回 `~6.0.3`，并在 `.github/dependabot.yml` 中忽略 `>=7.0.0`
   的升级，直到 typescript-eslint 支持为止
2. **重新提交 `web/bun.lock`**，并在 CI、Dockerfile、Makefile 中恢复
   `--frozen-lockfile`；Dockerfile 现在会先复制锁文件再安装依赖
3. 已验证：当 `package.json` 与锁文件不一致时，`--frozen-lockfile`
   会以明确的错误信息中止安装，而不是静默装上不同的版本

### 仍待处理

- **为 main 分支开启分支保护，要求 CI 检查通过后才允许合并**。这是针对本次
  事故直接原因的措施，目前尚未配置，红色 PR 仍可被合入。
