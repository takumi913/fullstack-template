# Solid 2 迁移消融实验

本实验比较迁移前基线与当前生产构建，并分别测量减弱动效、移除客户端脚本后的变化。结果仅代表这组页面、输入与实验环境，不能据此断言某个框架在所有场景下更快。

测量脚本：[`web/scripts/performance-ablation.mjs`](../web/scripts/performance-ablation.mjs)。原始数据：[`performance-ablation.json`](performance-ablation.json)。

## 对照组

| 标识                   | 内容                                                             | 可以回答的问题               |
| ---------------------- | ---------------------------------------------------------------- | ---------------------------- |
| `baseline-full`        | 提交 `143bee05162b12f23c3e7af7e8369d7a0c3ae73e` 的生产构建       | 整次迁移前后有什么变化       |
| `solid-full`           | 当前 Solid 2 生产构建                                            | 完整功能的现状               |
| `solid-reduced-motion` | 同一份 Solid 2 构建，模拟 `prefers-reduced-motion: reduce`       | 降低装饰动效的开销           |
| `solid-static`         | 同一份 HTML 与 CSS，仅在实验服务器内移除 script 和 modulepreload | 不运行客户端脚本时的展示成本 |

`solid-reduced-motion` 保留原有 JavaScript 下载与组件：CSS 停止过渡/动画、隐藏光标光效，点阵画布只绘制一次。它没有删除所有动效代码或监听器。`solid-static` 移除所有 script，包含主题初始化与 JSON-LD；它没有工具交互或客户端主题恢复，不能作为功能等价的发布方案。实验不会修改磁盘中的生产 HTML。

## 固定条件

- 页面：`/`、`/tools/json-formatter`、`/tools/word-counter`；均使用默认站点配置。
- 同一个独立 Chrome 进程，每次导航创建全新的浏览器上下文；关闭 HTTP 缓存、绕过 Service Worker，不共享 Cookie、存储或主题偏好。浏览器进程保持运行，不代表每次都冷启动浏览器。
- 视口 1280 × 800、DPR 1、桌面模式；CPU 限速 4 倍，网络延迟 40 ms，下载 200,000 B/s，上传 93,750 B/s。
- 各组使用同一实现的本地内存静态服务器、gzip level 9 与 `Cache-Control: no-store`。字体外部请求统一阻止，保留原 HTML，使用相同回退字体。
- 每组、每页预热 1 次，正式测量 7 次；共 84 次正式导航，另有 12 次预热。每轮轮换组别顺序，降低固定顺序带来的偏差。
- 正式采样期间不并行运行构建或测试。操作系统和宿主应用的负载仍可能造成波动，结果保留原始样本与四分位数。

CPU、浏览器、运行时版本及实际采样日期以 JSON 的 `environment`、`date` 为准。JSON 的 `bundles.*.sha256` 标识被测构建目录的内容；后续重新构建可能因工具链、代码或配置变化得到不同哈希。

## 指标口径

页面加载后再等待 1,800 ms，记录 FCP、截至此时的 LCP 和 CLS、下载的 JS 压缩字节数，以及累计脚本和主线程任务时间；随后等待 1,000 ms，用两次 `Performance.getMetrics` 的任务时间差记为“空闲任务时间”。这个等待窗口会有调度误差，没有按墙钟时间归一化。它是渲染进程主线程的任务计时，不是系统 CPU 占用率，也不包含 GPU 或合成线程。

`scriptMs` 是从导航到加载后观察点的累计脚本时间，包含持续动效；它不是单独的 hydration 时间。不同组的 load 时刻不同，累计观察时长也不同，`observedMs` 保留了实际时长。静态组中的少量脚本计时来自测量注入，应用 JS 下载为 0。`blockingMs` 是观察窗口内各长任务超过 50 ms 部分之和，不等同于 Lighthouse 的 TBT。LCP 仅来自有限观察窗口，本实验没有真实用户数据。客户端就绪检查位于随后的空闲窗口之后，因此这些加载指标也不能用作交互就绪耗时。

完整组与减弱动效组在加载指标采集后，通过主题切换确认客户端事件处理可用，再测量工具。因此首屏按默认深色测量，工具交互在随后切换的主题下测量，各交互组保持这一流程：

- JSON：粘贴包含 2,048 条记录的固定有效 JSON，触发 Ctrl+Enter，检查格式化后的 DOM 文本与标准输出完全一致。
- 字数统计：粘贴固定的 4,096 行英文文本，检查字符计数和单词计数更新为准确结果。
- 每次导航运行 7 次，每次输入略有变化；先取该导航内的中位数，再在 7 次导航之间汇总，避免把同一次页面内的重复操作视为独立样本。
- `commitMs` 从输入事件到正确结果写入 DOM；`frameMs` 再等待两次 `requestAnimationFrame`。这些是合成操作延迟，不是 INP，也不包含真实键盘/鼠标输入链路。

表格采用中位数；区间采用脚本定义的 p25–p75：对排序后的 7 个值取下标 `floor((n - 1) × p)`，不做插值。保留毫秒的小数只便于比较，不代表同等的测量精度。加载阶段与空闲窗口之后才运行工具，不把工具计算计入加载指标。

采样于 2026-10-21，Apple M1 Pro / macOS arm64，Chrome 156.0.8078.47，Bun 1.3.14。每个表格单元均可在原始 JSON 的 `summary` 与 `samples` 中核对；无显著性检验。

相对基线，完整组的首屏 JS 下载量减少 31.4%–32.6%，FCP 缩短 8.6%–8.8%；首页 LCP 缩短 54.3%，JSON 与字数统计页分别缩短 10.7%、8.7%。这是整次实现迁移的比较。

63 个 Solid 样本的 CLS 全部为 0，基线 CLS 中位数也为 0；基线 JSON 页另有 2/7 次出现 0.118 的布局位移，其余基线样本为 0。不能把实验中的零位移推广到字体网络、设备与内容不同的所有真实访问。

首页从完整组改为减弱动效，JS 下载量不变，空闲主线程任务从 72.42 ms 降至 0.39 ms，减少约 99.5%；LCP 中位数同为 624 ms。因此持续画布动画是当前首页空闲开销的重要来源，不能仅凭框架迁移假设持续 CPU 开销消失。工具页各组的空闲开销都很低，小差值不支持明确的性能结论。

静态组的页面 FCP 为 280–288 ms，说明客户端脚本及相关资源加载仍占有成本；该组缺少交互和部分 head 能力，仅作成本参照。

### 实验发现并修正的回退

第一轮完整测量发现首页 CLS 为 0.264，两个工具页为 0.118。布局位移来源指向工具下方的信任文案与后续内容，位移分别约 516 px、350 px。原因是异步加载函数返回重新包装的模块对象，丢失 Solid 2 构建器的模块标识，首次 hydration 无法复用同步预载模块：完整工具会短暂退回加载占位，再恢复实际高度。

修复后，路由使用直接 `lazy(() => import(...))`，SEO head 注册留在路由默认导出中；具名工具组件使用原生 `{ export: "ComponentName" }` 选项。构建检查同时要求首页布局、首页路由、工具路由与现有工具模块的预加载资源存在。三个页面的定位复测 CLS 均为 0，随后对最终构建重新运行全部正式采样。表格与原始 JSON 仅采用修复后的这一轮，不混合两个构建的数据。

## 如何复现

需要仓库指定版本的 Bun 与本机 Chrome；不需要另外安装浏览器驱动或基准依赖。从项目根目录执行：

```bash
snapshot=143bee05162b12f23c3e7af7e8369d7a0c3ae73e
baseline_dir="$(mktemp -d /tmp/solid-ablation-baseline.XXXXXX)"
git archive "$snapshot" | tar -x -C "$baseline_dir"
(cd "$baseline_dir/web" && bun install --frozen-lockfile && bun run build)
(cd web && bun install --frozen-lockfile && bun run build)
(cd web && bun run perf:ablation \
  --baseline "$baseline_dir/web/dist/client" \
  --snapshot "$snapshot" \
  --rounds 7)
```

脚本默认使用 macOS Chrome 路径；其他位置用 `--chrome /path/to/chrome` 或 `CHROME_PATH` 指定。`--output /path/to/result.json` 可以避免覆盖已保存数据。省略 `--baseline` 时只运行三组当前构建，正式样本数相应变为 63。运行期间暂停其他构建与测试。

基线源码只解压到临时目录，不重新引入当前仓库、依赖或 CI。完成后可删除本次创建的 `$baseline_dir`。浏览器使用独立临时配置，脚本结束时关闭并清理该配置。

## 结论边界与清理范围

迁移同时改变了渲染运行时、路由、状态管理、主题、国际化接入、构建与拆包；前后对比反映整个实现的变化，不能把全部差值归因于 DOM 更新机制。内部两组消融有助于识别动效与客户端脚本的成本，但也没有隔离每个依赖的贡献。静态组同时改变了 HTML 字节数和资源发现顺序，其差值也不等于纯 hydration 成本。

本次覆盖公开首页与两个工具页，不代表认证后台、大型列表或所有设备的表现。正式发布仍使用完整 Solid 2 构建；减弱动效遵循用户系统偏好。

清理审计覆盖受维护的源码、测试、注释、文档、依赖与锁文件、构建/格式化/检查配置、CI、容器构建及生成后的静态资源；移除了旧的路由配置、组件生成配置、测试适配器和状态/主题依赖。历史基线通过 Git 提交标识复现，不改写历史。

CI 通过 `seo:verify` 检查 hydration 预加载回归；浏览器消融采样按需运行，不将本机的绝对耗时作为跨机器性能阈值。
